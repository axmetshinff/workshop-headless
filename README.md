# Headless Bitrix — код воркшопа

API магазина на штатных механизмах ядра 1С-Битрикс: роутинг, `Engine\Controller`, `ServiceLocator`, конверт ответа.
Сквозной проект воркшопа «Headless Bitrix» (BXMax), модуль `bxmax.shop`.

## Что лежит в репозитории

Репозиторий — корень сайта Omut `~/Omut/shop.bitrix`. Git отслеживает только код проекта:

- `www/local/` — модуль `www/local/modules/bxmax.shop`, маршруты `www/local/routes/api.php`, настройки `www/local/.settings_extra.php`;
- `contract/` — эталонные ответы API и каталог кодов ошибок `errors.md`;
- `tests/` и `phpunit.xml` — тесты на Pest;
- `.github/` — шаблон PR для домашек;
- `README.md`.

Ядро (`www/bitrix/`), `www/upload/`, `vendor/`, `composer.json` корня сайта и `/bitrix/.settings.php` с паролем от базы в репозиторий не попадают.

## Требования

- Omut, сайт `shop.bitrix`, установка «Под ключ», редакция «Малый бизнес» или «Бизнес»;
- main 25.900+ (проверено на 26.1000), PHP 8.2+;
- `composer install` в корне сайта, чтобы работала консоль `php www/bitrix/bitrix.php`;
- с занятия 2: мастер «Интернет-магазин» с демо-данными и символьный код API `clothes` у инфоблока «Одежда».

## Тесты

Pest ставится в `composer.json` корня сайта. Этот файл не в git, поэтому на каждом стенде один раз:

```bash
composer config allow-plugins.pestphp/pest-plugin true
composer require --dev pestphp/pest
```

Composer выберет версию под ваш PHP: Pest 3 на 8.2, Pest 4 на 8.3, Pest 5 на 8.4. Запуск — из корня сайта:

```bash
vendor/bin/pest
```

Юнит-тесты не подключают пролог и не ходят в базу: `tests/bootstrap.php` регистрирует автозагрузку ядра и модуля, репозиторий в тестах подменяется реализацией из `tests/Fake/`.

## Раскладка модуля

Папки в `lib/` — по соглашению ядра: так раскладывают классы генераторы `make:*` и модули `sale`, `rest`, `iblock`.

| Папка | Что лежит | Кто кладёт |
| --- | --- | --- |
| `Infrastructure/Controller/` | контроллеры: вход в модуль по HTTP | `make:controller` |
| `Public/Service/` | сервисы сценариев — API модуля для контроллеров, агентов и других модулей | `make:service` |
| `Internals/Contract/Repository/` | интерфейсы репозиториев, без классов Битрикса | вручную, как в `rest` |
| `Internals/Repository/` | реализации: инфоблок, ORM | вручную |

Зависимости идут в одну сторону: контроллер → сервис → интерфейс ← реализация. Связь интерфейса с реализацией — в `services` файла `.settings.php` модуля.

Если вы привыкли к слоям из DDD: `Public/Service` — слой приложения, интерфейс в `Internals/Contract` — порт, реализация в `Internals/Repository` — выходной адаптер, контроллер — входной адаптер. Отдельной папки `Domain` у ядра нет: `Public` и `Internals` делят код по тому, что модуль разрешает вызывать снаружи.

## Контракт API

Ответы контроллеров `/api/v1` приходят в конверте ядра (`Bitrix\Main\Engine\Response\AjaxJson`):

```json
{"status": "success", "data": {}, "errors": []}
```

- Успех: `status: "success"`, данные в `data`, `errors` пустой.
- Ошибка приложения: `status: "error"`, `data` может быть `null`. Решения принимаем по `errors[].code`: коды стабильны, их список — в `contract/errors.md`. `message` показываем покупателю только у ошибок, которые API отдаёт явно.
- На проде (`exception_handling.debug = false`) у непредвиденных ошибок `message` равен `Internal server error.`, начиная с main 26.1000.
- HTTP-статус проверяем отдельно: `401` — нужен вход, `404` в конверте — ресурса нет, какого — скажет код ошибки. Неизвестный адрес `/api/v1/*` перехватывает catch-all маршрут: он отвечает `404` и `{"status":"error","message":"Endpoint not found"}`. Ответ `500` без конверта — сервер упал до контроллера, разбирать тело не нужно.
- Список товаров отдаёт `id`, `name`, `code`, `price`. Карточка `GET /api/v1/products/{id}` — те же поля плюс `categoryId`, `article`, `descriptionHtml`. Описание всегда HTML: текстовое описание из админки приходит экранированным.
- Неактивный товар неотличим от несуществующего: в списке его нет, карточка отвечает `PRODUCT_NOT_FOUND`.
- Суммы — строкой с двумя знаками после точки и валютой: `{"amount": "1990.00", "currency": "RUB"}`.
- `GET /api/v1/basket` возвращает корзину текущего браузера и `csrfToken`. Не закрываем сессию до действия: `Fuser` создаёт и запоминает анонимного покупателя.
- `POST /api/v1/basket/items` добавляет позицию или увеличивает уже существующую. `PATCH /api/v1/basket/items/{id}` меняет количество, `DELETE` удаляет позицию. Успешная мутация возвращает корзину целиком.
- Все мутации корзины требуют cookie той же сессии и заголовок `X-Bitrix-Csrf-Token`. POST и PATCH принимают только `application/json`; DELETE тела не ждёт.
- `productId` — ID покупаемой позиции каталога. Для товара с предложениями передайте `id` выбранного объекта из `offers`.
- `quantity` — целое число от 1 до 100. Цена, валюта, название и provider из JSON не принимаются: их определяют модули `catalog` и `sale`.

Эталонные ответы — в `contract/`. Формат меняется только вместе с ними и с версией в адресе.

## Связи каталога

`GET /api/v1/products/9?include=offers,images` добавляет в карточку предложения и фотографии. В списке тот же параметр добавляет поля в каждый товар. Можно запросить одну связь. Без параметра или с `include=` API отдаёт прежний набор полей. В списке через запятую регистр имён значим, пробелы вокруг имён разрешены, повторы учитываются один раз. Неизвестное имя, пустое имя между запятыми и массив `include[]` дают HTTP 400 с кодом `INVALID_INCLUDE`.

- `offers` содержит активные предложения, упорядоченные по ID. У предложения есть `id`, `name`, `size`, `color`, `price`, `available`. Размер и цвет содержат подпись из каталога или `null`. Цена имеет тот же формат, что у товара. Для демомагазина берём цену BASE без количественных ступеней. При отсутствии цены возвращаем `null`. Значение `available: true` требует и цены, и флага каталога `AVAILABLE=Y`. Корзина повторно проверяет условия покупки при добавлении.
- `images` содержит абсолютные HTTP(S)-адреса фотографий родительского товара. Сначала идёт детальная картинка, затем картинка анонса и файлы свойства `MORE_PHOTO`. Если разные ID файла ведут на один URL, в ответе остаётся его первое вхождение. Для локального пути ответ сохраняет схему, имя хоста и порт запроса.
- Если у товара нет запрошенных предложений или картинок, соответствующее поле содержит `[]`.

Для этого занятия нужен демокаталог мастера «Интернет-магазин». У родительского инфоблока символьный код API `clothes`. В инфоблоке предложений мастер использует общую таблицу свойств (версия 1). Отдельный символьный код API для него не требуется. Связь хранится в `CML2_LINK`, размер в `SIZES_CLOTHES` или `SIZES_SHOES`, цвет в `COLOR_REF`. Подписи цветов берём из highload-блока `ColorReference`.

### Страницы и сортировка

`GET /api/v1/products?page=1&pageSize=2&sort=name&order=desc` возвращает первые два товара по названию в убывающем порядке. Нумерация начинается с 1. По умолчанию размер страницы 20, допустимые границы от 1 до 50. Значения ниже границы приводятся к 1, размер выше 50 приводится к 50. За последней страницей ответ содержит `items: []`, запрошенный номер страницы и общее число активных товаров в `meta.total`.

Параметр `sort` принимает `id` или `name`. Направление по умолчанию `asc`, также доступно `desc`. Регистр направления можно менять. При равных названиях вторым ключом служит ID по возрастанию. Без обоих параметров сохраняется порядок мастера `SORT ASC, ID ASC`. Незнакомое поле даёт `INVALID_SORT`, неизвестное направление или `order` без `sort` даёт `INVALID_ORDER`. Все три ошибки параметров каталога возвращают HTTP 400.

### Эталоны занятия 4

Файл `contract/product-with-relations.json` снят с карточки 9 с обеими связями. `contract/products-with-images.json` содержит ответ на `/api/v1/products?pageSize=2&include=images&sort=id&order=desc`. В `contract/product-empty-relations.json` лежит модельный пример товара без фото и SKU. Его проверяет `ProductViewServiceTest`. Коды ошибок и действия клиента описаны в `contract/errors.md`.
